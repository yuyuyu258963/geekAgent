# geekAgents


用 TypeScript/Node.js 动手实现一个最简单的 Agent/Harness，从零实现 REPL 循环与流式多轮对话。
- R：read 捕获并解析输入
- E：执行并更新状态
- P：序列化并展示结果
- L：尾递归/事件复盘

# Day1：一个最简单的 Agent 的 REPL 地基

## REPL 是什么

REPL 是 Read-Eval-Print-Loop 四个词的缩写，翻译过来就是 【读入 -> 求值 -> 打印 -> 再循环】。这个模式实际上就类似于常用的命令行、Python 交互式解释器、node 不带文件名直接敲，全都是 REPL：打一行、回一句、光标又亮起等下一行

为什么 Agent 的地基要选 REPL？因为人和模型对话的本质就是【一来一回循环】：我们输入、模型答、再输入... 一个会反复收集输入的循环，恰好就是 REPL 的本意。所以第一阶段就是先把这部分能反复聊的循环跑通，后面加工具、加文件读写，都是在循环中塞新的东西

## 为什么不直接用 curl

可能会想：调模型不就是发个 HTTP 请求嘛？curl 一行搞定，为什么还需要写多余的代码
Day1 REPL 的好处有：
- 连续对话：输入后自动进入下一轮
- 多轮记忆：history 自动累积并重发
- 流式输出：收到一个片段就打印一个
- 信息区分：用户、模型、系统分别着色

# Day2 工具调用循环
Day2 实现工具调用循环：模型可以请求 get_current_time, 程序执行后把真实时间返回模型，为后续命令与文件工具打下基础

## 设计：先约定工具、消息和结果
1. 工具 = 一个对象。名字 + 描述 + 参数 JSON Schema + 一个 run 函数。模型只会看到清单声明的工具，run 才是真实世界
2. history 依然是那个数组。工具调用只是一种新的 message 角色：assistant 发起 tool_calls，以及回传的 tool 消息
3.  结果只有字符串。工具 run 的结果一律转成字符串回传给模型。真实世界（时间、命令输出、文件内容）最后都折叠成一行文本，模型层面不需要任何结构化协议

# Day3 Bash 工具
在编程 Agent 的世界里，只要模型能跑一条 shell 命令，几乎就等于拥有了所有能力 —— 读文件靠 cat/ head，列目录靠 ls，搜代码靠 grep/ rg。换句话说，一个能用的 bash 工具，在能力上已经囊括了后面要做的 read/ glob/ 写文件/ 搜索等所有专用工具。正如 Andrej Karpathy 一类“给模型一个终端基本就够”的观点出圈，也成为很多早期 Agent（如 SWE-agent）把 bash 当作住交互界面的原因。
但这句话口号只说对了一半：bash 能做很多事，也意味着能造成很大影响。cat 和 rm -rf 都从同一个入口执行，所以不能把模型生成的命令直接交给系统。我们用 run_shell 接入 bash，同时加入超时、输出阶段和执行前确认，并把确认做成可替换的函数

## 为什么 shell 不能直接裸跑
`bash -c <command>` 本身只是一行，但模型生成的命令可能出错，也可能影响工作区之外的内容。我们先加三项最基本的限制：
1. 超时：模型让跑 sleep 999 或一个挂起的命令，没有超时就会永久阻塞 请求 -> 执行 -> 回传 的循环，agent 直接卡死
2. 输出阶段：模型让跑 cat 几个 G 的日志或 find /, stdout 能瞬间撑爆上下文窗口，把前面的对话全挤掉。截到 2000 字符是保底
3. 执行前确认：命令可能是 rm -rf。当前先使用 y/n，并把确认逻辑独立成一个函数，后续的权限模型（白名单/ask/allow/deny）直接替换它

## 设计：确认留在工具内部
前面的工具循环已经能处理任意工具的 run，因此这次只是新增 shell 工具，不修改循环体。关键设计决策：
确认发送在工具 run 内部，而不是在循环里

```
chat.ts 循环（Day 2 原样，未改）：
    for 每一轮:
        发请求 → 流式收 → 若有完整 tool_calls：
            逐个 execTool(name, args)
                ↓
        run_shell.run(args)  ← Day 3 新增，循环对此无感知
            1. 解析 command
            2. await confirm(...)   ← 可注入的确认（本行调用的 confirm 由 setConfirmFn 注入）
            3. bash -c 执行（带 timeout）
            4. 合并 stdout/stderr + 截断
            5. 返回字符串
            ↓
        结果以 role=tool 回传，模型继续
```
这样 execTool 不知道也不关心【这个工具要不要确认】 —— 确认的细节完全封装在 run_shell.run 里，它只调用一个 confirm 函数变量。后续升级权限时，只需要通过 setConfirmFn 把 confirm 换成白名单/allow/deny 实现，循环和其他工具都不用动

# Day4 文件工具与注册表
> Day3 只给模型了一扇门：run_shell。读文件要被反复过问，改代码只能用 echo > / sed, 改了什么看不见、确认是对整条命令拍板。Day4 一次把这两端都拆出来：读奏免确认的专用工具（ls/ read/ glob），写走展示 diff 再落盘的专用通道（write/patch），顺手把攒下的 7 个工具统一进一个注册表。此时模型一次走通 [读 -> 改 -> 验证] 的闭环

## 为什么同一个 shell，撑不住读写两端
将自己带入模型的处境：想改代码，第一件事永远是先弄清楚项目长什么样。可就算只是 cat 一个文件，也得先调 run_shell、再等一个 y/N。读一个文件确认一次，读 10 个文件确认十次，光点确认就够累了。
再深想一层：**读** 本身毫无破坏力，看文件永远不会让机器变坏。可为了能干活，读和写被绑定再了同一个口子上 —— run_shell 什么命令都放行，所以它也永远不会被设为确认。也就是这里将一个明明无害的操作和危险的命令放在一起，每从而造成了运行效率的低下。
而再模型真想改代码，能用的还是 echo > / sed，这里有三个问题：
1. 改了什么，不可预览。sed -i 's/foo/bar/' day4/x.ts 一敲回车，这次改动需要等写完 read 一遍才知道。它本质上是一次看不见的破坏
2. 确认的粒度太粗糙。y/N 是对整条命令拍板，一条 sed 完全能一口气改十个地方，人却只能给一个“同意”。想看清楚模型具体要改动哪几行，无从谈起
3. 改错的代价是静默。模型对着几百行的文件拼正则、数行数，一个字符错位文件就悄悄坏了，还没有后悔药（回滚是后续的事）
所以本小节需要解决的问题比较明确了，读取和写入共用 run_shell，权限粒度太粗。我们把读取做成不含写能力的专用工具；写入也使用专用工具，并在落盘前展示 diff

# Day5 历史压缩
在前 4 天的内容中已经接通对话、工具和文件操作，但它们都依赖 Chat 中的 history。这条数组会随着用户消息、模型回答和工具结果不断增长：
1. 每轮先放用户消息
2. 再把回答放回去
3. 工具结果也放回去
每次发请求，都是把整条 history 全量送给模型是（chat.ts 里那行 messages: this.history）。这会导致上下文的内容暴涨。常见的处理方式有：
|方式|优点|代价|
| - | - | - |
|全部保留|信息最完整|最终超过上下文窗口，成本和延迟持续增加|
|只留最近 N 条|实现简单，长度稳定|旧决定和关键线索直接丢失|
|摘要旧消息|用较少文字保留主要信息|摘要本身会丢细节，还要多调用一次模型|

## 目标：自动压缩 + 手动入口
验收标准：
1. history 字符数超过阈值后，下一轮正式回答前先调用模型，把较早的多条消息替换成一条“此前对话摘要”
2. 最近 6 条消息保留原文；压缩完成后继续追问早期事实，模型仍能从摘要中找回关键内容
3. /compact 可以不等阈值手动执行同一逻辑，并显示本次合并了多少条旧消息

# Day6 多轮对话与持久化
> Day5 中已经能压缩一条过长的 history，但所有话题仍然在一个数组中：上午改代码、下午查资料，模型每次都要同时看到两边的上下文。
> 现在要做的就是让一个进程内可以同时维护多条互相独立的会话（/new 、/sessions、/open），再把整个会话集合连同当前 ID 一次落成 JSON

## 目标：会话可以切，也可以跨进程
验收标准：
- /new work 创建空会话，/open <id> 来回切换后，每条会话仍保留自己的消息，/sessions 能看到当前会话与消息数
- /save 把全部会话及当前 ID 写入 .geekagent/sessions.json, /load 回复后仍停在保存时的会话
- 正常退出会自动保存；临时的 default 会话会获得可再次打开的 ID，重启后可以继续此前的对话


## 为什么补创建多个 Chat
最直观的做法是每条会话创建一个 Chat 对象。但 Chat 里除了 history，还有 OpenAI client、模型配置和完整工具循环。复制多个对象只是为了保存多条数组，职责太重。所以我们仅保留唯一的 Chat，新增 sessions 管理 Map<string, Message[]> 。切换时，先把 Chat 当前的消息交还给 Map，再把目标数组放进 Chat。模型调用逻辑完全不需要认识“会话”

## 存档长什么样
存档只有两层：current 记录当前 ID，sessions 保存 ID 到 message 数组的映射
```json
{
  "current": "work",
  "sessions": {
    "default": [],
    "work": [
      { "role": "user", "content": "继续实现 Day 6" },
      { "role": "assistant", "content": "好。" }
    ]
  }
}
```

# Day7：支持轻量 TUI 与常驻面板
> 前面的终端只会不断追加日志，本轮使用多少 token、上下文还剩多少空间都看不到。今天让程序接管终端：左侧保留消息流，右侧常驻用量面板，持续显示本轮/累积 tokens 与上下文占用。退出后恢复原来的终端内容

## 为什么需要一块一直留在屏幕上的地方
除了聊天的内容，其实用户也想看到其他两样东西：
1. 本轮/累计 tokens
2. 上下文占用
这两类数据都需要固定显示，普通日志流做不到。因此我们使用全屏 TUI，把消息区、输入区和状态区分开；后续新增展示型状态时，也可也继续放进右侧面板

# Day8 权限与回滚

## 为什么确认框不等于权限
前面解决的是“执行这一次命令前问一句”，并没有回答三个更长期的问题：
1. 一个只读工具是否可以一直放行
2. 一个不希望 Agent 使用的工具，能否入口直接拒绝
3. 文件工具即使免确认，能否保证它只看当前项目

把答案写死在工具里，每次换项目都要改 TS。更麻烦的是，read ../../.env 仍然属于“只读”，却已经超过了项目边界。我们需要的不是更多确认框，而是一张独立于工具实现的权限表，以及一条所有文件路径都必须经过的边界线
工业级 Agent 往往还会使用操作系统 sandbox、容器或更细的命令规则。当前先在应用层实现四个最容易观察的边界；它能减少误操作，但不等同于操作系统级隔离

## 目标
1. .geekagent/GeekAgent.json 为每个工具配置 allow、ask 或 deny：分别直接执行、询问后执行或在进入工具前拒绝；
2. ls / read / glob / write / patch 只能访问配置的 root，相对越界、绝对路径和借符号链接越界都会被拒绝；工具返回中的密钥会被替换
3. write 和 patch 真正写入前把旧内容保存到 .geekagent/undo.json, /undo 能恢复被覆盖的文件或删除刚创建的文件
